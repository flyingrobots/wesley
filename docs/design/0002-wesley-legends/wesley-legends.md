---
title: 'Wesley Legends'
---

## Sponsors

- Human: I can look at Wesley's backlog or design packets and understand which
  enduring product domain the work belongs to.
- Agent: I can classify new work into a stable legend set without inventing new
  domains every few cycles.

## Hill

Wesley's legends become a finite, repo-grounded set of enduring product domains
that organize attention across cycles without collapsing into milestones,
pillars, or invariants.

## Playback Questions

### Human

- [ ] Can I read the legend docs and understand which broad domain owns schema
      semantics, transmutation breadth, runtime behavior, and
      evidence/judgment?
- [ ] Do the legend scopes feel like real Wesley domains instead of process
      theater?

### Agent

- [ ] Can I classify most Wesley work into one of the legends without
      stretching the definitions?
- [ ] Does each legend guard a coherent subset of invariants and ask standing
      playback questions that fit the domain?

## Accessibility and Assistive Reading

- Each legend file should front-load scope, guarded invariants, and standing
  playback questions.
- The legend index should read cleanly as plain Markdown without requiring a
  diagram.

## Localization and Directionality

- Legend names should be short, stable, and literal.
- Scope text should prefer domain nouns over metaphor.

## Agent Inspectability and Explainability

- The legend set should be finite and explicit enough that future backlog items
  can use legend prefixes without guessing.
- Legend docs should distinguish domains of attention from product pillars and
  from invariants.

## Non-goals

- [ ] Building a complete backlog under every legend in this cycle.
- [ ] Forcing every file or package in the repo to belong to exactly one legend.
- [ ] Turning legends into milestones, teams, or release trains.
